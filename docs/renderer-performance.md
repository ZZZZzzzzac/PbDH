# 渲染性能测量

## 范围与复查

`npm run measure:renderer` 接入根目录 `npm run verify`，输出两类独立证据：

- SSR：固定敌人模板 `1.0.0`、一次预热、60 次 `renderToStaticMarkup` 的 P95。不是浏览器布局、图片解码或交互耗时。
- 生产构建：使用 Platform 实际 Vite 配置，从 entry 沿静态 imports 遍历初始 JavaScript 闭包，报告原始/gzip 字节及其中的模板渲染器、编辑器版本。独立动态 chunk 的存在不等于它没有被初始静态 imports 引入。

`fixtureMediaFileBytes` 只是单份测试图片的文件字节，不是浏览器内存。脚本不输出虚构的目录规模、卡面挂载数或堆内存数据；SSR 的有限性检查也不是性能预算。

浏览器挂载测量使用仓库规定的 Browser 插件，对真实本地页面读取 DOM。不要用 SSR、happy-dom 或源码字符串检查代替实际页面证据。也不要在浏览器测量时改动现有角色或上传测试数据。

## #66 按需加载后的复查

2026-09-09，同一环境的生产构建测得：初始 JavaScript 1,448,321 字节，gzip 427,566 字节；初始静态闭包中的渲染器与编辑器版本均为 0，全构建仍保留各 40 个版本。后续微小代码修改会影响字节数；版本数与依赖闭包由统一验证重新计算。

- App 改用 `@pbdh/templates/frontend/lazy`；依赖检查阻止重新导入同步前端注册表或其私有实现路径。
- 渲染器和编辑器分开请求。同一精确版本共享在途请求及成功结果；一次重试会更新使用该版本的全部组件。
- 未显示的 App 保留控制器、账号及回收站注册，但不挂载卡面和编辑器。页面切换仍会重新调度被聚焦状态暂停的云同步。
- 封面生成在一次操作内复用各版本的加载结果，避免网络失败时按资源数量反复请求。
- 同步入口保留给契约验收和离线工具；SSR 测试先显式加载测试涉及的精确版本，再检查输出，不假装 SSR 会执行客户端加载效果。

边界：此修改把历史渲染器和编辑器移出初始加载，不代表所有 Template Core 目录、Schema 或应用代码都已按需加载。版本清单和公共底座仍有成本；某版本可以复用旧实现作为依赖。已访问模块会留在浏览器模块缓存中，页面切换不等于卸载已下载代码。后续修改公共排版组件或字体时，仍需检查受影响的历史版本，不能仅靠冻结版本目录承诺跨环境逐像素一致。

## 历史版本增长的成本

2026-09-09，在 `e162981` 上扩展构建测量：初始闭包包含 **40 个 Core capability 版本**，即全构建的全部 40 个；渲染器和编辑器仍各为 0。初始 JavaScript 为 1,450,904 字节，gzip 428,492 字节。这不是 Core 单独占用的字节数，也不是浏览器网络实测。脚本现在持续输出 `initialCoreVersions` 和 `allCoreVersions`，避免把前端视图实现的延迟加载误报为整个模板的延迟加载。

设 N 为历史模板版本总数，K 为一次实际工作流用到的精确版本数；以下是成本模型，不是对尚未构建的版本规模作性能预测：

| 成本 | 随版本增长的表现 | 按需加载能否消除 |
| --- | --- | --- |
| 浏览器首屏模板代码 | 当前 Core 注册表仍静态引入 N 个能力模块；视图实现已延迟加载 | 尚未完全消除，需要拆分轻量目录与能力实现 |
| 本次工作流的视图代码 | 取决于 K 个版本及其共享/历史依赖的并集，不必等于 N | 可以降低；不能把 K 简单当作实际模块数 |
| 长时间使用后的模块缓存 | 随本次页面生命周期访问过的版本及依赖增长 | 页面切换不回收模块缓存 |
| 发布物体积、构建工作量 | 保留全部历史实现，随历史源码和依赖总量增长 | 不能消除；共享实现可减少复制 |
| 外观回归验收 | 共享排版或字体变化可能影响多个历史版本；覆盖面还乘以代表性内容和目标环境 | 不能消除，只能选择明确的支持范围和测试矩阵 |

“保留旧版本”与“任意环境逐像素相同”不是同一承诺。前者要求资源引用不被自动升级，并保留对应实现；后者还受字体文件、共享 CSS/组件、浏览器排版与缩放等条件影响。仅冻结版本目录不够。将旧卡导出为固定图片可以保存一份外观，但不能替代可编辑、可交互的卡面，因此不是当前方案的默认退路。

待完成的边界是：菜单只加载轻量目录；打开资源包或文档时加载它引用的精确 Core 能力，以及明确需要的依赖；仅在用户选择升级时加载升级路径。外部文件校验不能因模块尚未加载就直接放行，也不能把“未加载”误判为“不支持”。完成后应以初始能力模块清单和多版本工作流的实际加载记录验收，而不是只看动态 chunk 是否存在。

本节是成本评估及未完成项记录，不变更已经接受的历史兼容承诺。当前 #66 的证据只足以确认渲染器/编辑器按需加载，尚不足以证明“只加载当前资源包所需的全部模板能力”。

## Core 静态依赖迁移结果

2026-09-09，迁移 Player 保存和替换入口、Creator 右键菜单后，实测初始 JavaScript 为 1,395,396 字节，gzip 408,614 字节。初始静态闭包中的 Core capability、渲染器和编辑器版本数均为 **0**。测量脚本现将三者均列入门禁；历史能力、渲染器和编辑器仍由精确版本动态清单保留。

这取代上节“首屏静态包含 40 个 Core”的当前状态，不抹去其历史基线。轻量目录、公共代码和 Contract 数据仍有成本，不能称为模板相关字节全部为零。

运行时验收仍未完成：`use-creator-document-persistence.ts` 的桌面列表恢复会调用 Repository 的全列表校验，而模板状态校验已改为动态加载引用能力。因而即使静态门禁通过，后台恢复仍可能加载不可见文档的模板。需要继续收敛恢复范围，并以真实页面启动、切换和错误重试的动态加载记录验收；不能用静态闭包的零值代替这一证据。
