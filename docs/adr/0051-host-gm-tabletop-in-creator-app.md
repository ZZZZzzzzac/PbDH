# Host GM Tabletop in Creator App without Merging Documents

Status: accepted

PbDH keeps `Creator App` and `GM Tabletop` as separate L1 product capability boundaries, but hosts both in one Creator App entry point and deployment under `apps/creator`. `GM Tabletop` replaces the former `GM App` product name. Product hierarchy continues to describe independently acceptable user capabilities; it does not require one frontend deployment per L1.

Creator App owns the only mutable Resource Package workspace model. A Creator Workspace remains one mutable Resource Package project and exposes the complete Creator authoring capability set. There is no GM Resource Workspace, GM Resource Package Ingress, GM workspace repository, or restricted GM workspace Capability Set. A GM who organizes, copies, imports, converts, or edits resources in the left workspace area is using Creator capabilities and creates ordinary local or private Creator Workspaces. Combining resources from several packages continues to use Creator's explicit copy-to-package workflow and creates a new Resource Package identity.

GM Tabletop owns Tabletop Documents and Tabletop Instances but not source Resource Workspaces. It appears as a special document tab inside Creator App and can browse resources across the App's Creator Workspaces. Selecting, importing, opening, or focusing a resource never places it automatically. Only an explicit placement command copies the current Game Resource definition and required Replacement closure into a new Tabletop Instance Resource Copy. Later workspace edits, imports, replacement, deletion, Market updates, or source loss never change an existing instance; the Tabletop cannot refresh, rebind, migrate, or write an instance back to a Workspace.

Resource Package files, third-party formats, Creator operations, and Market handoff all enter through Creator's ordinary Resource Package or Resource Conversion workflows. Market's “open in GM Tabletop” action opens Creator App, imports or opens the current complete Resource Package under Creator rules, opens or focuses a GM Tabletop tab, and may focus the selected Resource ID. It never creates a single-card package, never creates a Fork, and never places a card silently. “Adapt in Creator” is a different, explicit action available only from a published Market resource: it creates a new private draft Package ID carrying the selected Publication as pending Fork source. That relationship becomes a Market Fork only if the user later publishes the draft. Resource License content is displayed but never gates either flow.

Creator and Market expose the same user action, “send to tabletop”. After any required Creator import, update, or explicit conflict resolution has completed, the user selects one existing GM Tabletop Document as the destination. Creator Ingress never auto-Forks; cancelling a conflict changes nothing, while any explicit save-as-new action creates an unrelated draft unless the user entered through Market's separate Fork action. If no tabletop exists, the App prompts the user to create one before continuing. Selecting or creating the destination opens that tabletop and preserves the source-resource focus, but placement still requires a separate explicit command. Resource-browser search, filters, expanded state, recent resources, and recent workspace or tabletop choices are device-local UI state and do not enter the Tabletop Document.

Creator Workspaces and GM Tabletop Documents remain independent local-first documents even though one App hosts them. They have separate stable IDs, payloads, lifecycle, synchronization, conflict handling, deletion, recovery, import, and export. The shared Cloud Document Service therefore supports Character Save, Creator Workspace, and GM Tabletop Document kinds; there is no GM Resource Workspace document kind. Creator Workspaces export complete `.pbres` files under Creator ownership and publication rules. Each GM Tabletop Document exports one self-contained `.pbtab`; there is no first-version bulk tabletop export.

Creator and GM workflows use the same left-side Creator Workspace and therefore the same Workspace destructive-operation flow. Deleting Workspace resources, clearing Workspace content, or another destructive Workspace operation uses Creator-owned warning and confirmation rules regardless of whether the active document tab is a Creator editor or GM Tabletop. Tabletop-instance edits, removals, clearing, placement, state changes, and private-copy changes execute directly as explicit tabletop commands. The first version provides no undo/redo, persistent command history, or separate tabletop deletion confirmation flow.

The first frontend composition roots are `apps/player`, `apps/creator`, `apps/market`, and `apps/backend`. Creator App resolves and injects Template authoring, Resource Conversion, Canonical Resource Renderer, and GM Tabletop capabilities. Shared packages remain unaware of the host and preserve the one-way dependency rules.

This decision supersedes ADR-0048. It supersedes the four-entry-point or separate-GM-App portions of ADR-0004, ADR-0005, and ADR-0012, plus the separate-GM-App, GM Resource Workspace, GM ingress, deployment, release, session-switching, and cloud-document-set portions of ADR-0006, ADR-0010, ADR-0019, ADR-0020, ADR-0034, ADR-0036, ADR-0043, and ADR-0049. Their remaining identity, backend, role, contract, snapshot, session, dependency, explicit-update, and cloud-migration decisions remain accepted. Earlier ADR references to `GM App` that concern tabletop rendering, behavior, instances, or permissions are interpreted as references to the Creator-hosted `GM Tabletop` capability.

## Consequences

- Creator and GM workflows share one application and local resource list without merging Creator Workspace and Tabletop Document data.
- Creator and GM workflows share one Creator-owned Workspace warning and confirmation interface; GM Tabletop does not duplicate that interface or add undo/redo for tabletop commands.
- GM campaign preparation that combines resources creates an ordinary Creator Resource Package project rather than a non-exportable private package type.
- Workspace editing uses Creator authorization. Tabletop Capability Sets still gate tabletop commands and instance-private definition editing independently from Player Tabletop capabilities.
- Creator-to-GM snapshot transfer and GM same-Package-ID replacement rules are removed. Creator Workspace import, update, no-op, cancel, replace, and explicit save-as-new rules are the only mutable package rules in this App; none automatically creates a Fork.
- Creator and Market use one “send to tabletop” destination-selection flow. It selects an existing tabletop or prompts creation when none exists, and never treats destination selection as placement.
- Creator App can remain fully local and offline for both resource preparation and tabletop operation without cross-origin browser-storage transfer.
- L1 PRDs, domain terminology, C4 views, roadmap, Contract requirements, Cloud document kinds, and Market handoff acceptance must use this hosting model.
