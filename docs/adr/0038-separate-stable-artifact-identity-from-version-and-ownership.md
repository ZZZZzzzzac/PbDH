# Separate Stable Artifact Identity from Version and Ownership

Status: accepted

Stable IDs answer whether two artifacts are the same logical thing; SemVer and snapshots answer which content version is being used; ownership answers who may publish or govern it. PbDH keeps these concerns separate.

System Package IDs and Resource Package IDs are globally unique and remain stable across their versions. Resource IDs are stable only inside their owning Resource Package and need not be globally unique. Any reference that crosses a package boundary therefore uses the pair `(Resource Package ID, Resource ID)`, called a Game Resource Reference.

Resource Template IDs and Resource Conversion Adapter IDs are assigned by the Platform Administrator because their implementations enter the trusted App release boundary. Ownership is stored as a separate relationship rather than encoded into an ID, username, or other mutable account attribute.

When Market first accepts a Resource Package ID, it binds that ID to the publishing Account ID. Only that owner, or a future owner established through an explicit transfer mechanism, may publish another Market snapshot under the same ID. Copying or adapting another package is a Fork and must receive a new Resource Package ID; preserving package-scoped Resource IDs inside the Fork is allowed because the new package identity keeps references distinct.

The first Market release supports one owning author only and no ownership transfer. The system derives a Resource Package Snapshot Digest from canonical logical content solely for exact equality, integrity, idempotent retry, and same-version/different-content detection. Its exact algorithm is part of the versioned Resource Package Contract: version 1 uses SHA-256 over a deterministic, type- and length-framed byte stream with a `pbdh-resource-package-digest-v1` domain identifier, RFC 8785 JSON Canonicalization Scheme (JCS), and Contract-defined ordering. Contract validation precedes canonicalization and rejects duplicate object names, invalid Unicode, and values outside the supported canonical JSON domain. JCS does not NFC-normalize authored string values: ordinary text preserves its code points and visually equivalent but code-point-distinct text produces a different Digest; portable paths follow their separate normalization rules. Its input includes package metadata, canonical resource and relation JSON, normalized relative paths, Asset IDs, and normalized media bytes. ZIP entry order, compression, archive timestamps, export time, machine paths, UI state, and the claimed Digest field itself are excluded. Directory organization is observable package content, so a path-only move changes the Digest without changing Resource identity and normally requires only a package `PATCH`. A Portable Archive may carry the claimed Digest, but every consumer recomputes it under the exact Contract and trusts only the computed result; Market persists its own computed value rather than accepting the client's claim. The Digest is not an artifact identity, version, provenance, ownership, author-maintained field, signature, or proof of authenticity. Publishing the same Package ID, SemVer and computed Digest is idempotent; the same version with different canonical content is rejected, and a new current snapshot must use a strictly greater SemVer. Withdrawing and restoring the unchanged last snapshot does not create a new package version.

Resource Package SemVer expresses only the minimum structural compatibility the platform can prove; it never interprets game balance, formula meaning, or rules text. Removing or changing a Resource ID, changing an existing resource to an incompatible Template `MAJOR`, changing the Target System Package ID or target `MAJOR`, or breaking package relations requires `MAJOR`. Adding Resource IDs or non-breaking relations requires `MINOR`. Existing field values, text, media, tags, paths, display metadata, license, provenance, and target `MINOR`/`PATCH` changes require at least `PATCH`. A Creator may choose a higher version or skip numbers but cannot publish below the provable minimum. Thus even a dramatic value change such as `1d6` to `1d20` has only a platform-computed `PATCH` minimum; choosing a semantic `MAJOR` remains the author's decision.

## Consequences

- Renaming an account or transferring ownership does not change artifact IDs or break references.
- Two packages may contain the same Resource ID without collision. Character Saves and provenance records must never persist a bare Resource ID.
- Releasing a new version keeps the same package ID; creating a Fork uses a new package ID.
- Market rejects attempts to publish an already-bound Resource Package ID from another account instead of treating them as updates.
- Explicit local file import may still replace a local package with the same ID because the user selected that file; Market ownership guarantees do not imply that offline files are platform-authenticated.
- A matching claimed and computed Digest detects accidental corruption but does not establish authorship or prevent a modifier from changing content and recomputing the claim; the first release has no Resource Package signing system.
- Every supported implementation must pass the same cross-language known-answer Digest fixtures. Changing the digest algorithm, domain identifier, canonicalization, framing, or ordering requires a new Resource Package Contract version; version 1 does not use a Merkle tree, custom cryptography, or a separate incremental-digest protocol.
- Digest fixtures include object-key ordering, escaping, duplicate-name rejection, invalid Unicode rejection, composed/decomposed ordinary text, and separately normalized portable paths so implementations cannot silently normalize authored content.
- Public author credit may include non-authoritative text, but only the bound Account ID can update or withdraw the Publication.
- Exact identifier encoding and generation algorithms may be chosen with the Contract Schema, but they must support offline creation without requiring a live Market reservation.
