# 文本整理与语义映射

本参考适用于原生文本，以及第三方 Adapter 留下的待裁定记录。

## 建立可追溯副本

先完整复制来源，再在副本中工作。保持可追踪的来源位置，例如文件名、标题、页码、表格行或原始记录 ID。剥离内容时记录理由：`package-metadata`、`navigation`、`narrative`、`duplicate` 或 `pending`。

“看起来不像卡片”不是删除理由。战役背景、使用说明、版权声明、资源目录和游戏资源可能混排；边界不明确时保留上下文并问用户。

## 统一格式后再提取

每种资源建立一种统一、可人工阅读的中间结构，至少清楚表示：

- 资源起止边界与层级/文件夹；
- 名称、原文名、类型；
- 普通字段；
- 简介或风味内容；
- 有序特性及其名称、原文和描述；
- 图片引用、署名与来源；
- 任何拆分、合并或替换关系。

只规范标点、Markdown 和标签表达，不趁机改写规则。保留数值、骰式、资源消耗、条件、顺序和强调语义。

## 模板选择

以当前 `currentTemplates` 和每个模板 Schema 为准。优先使用能完整表达来源语义的专用模板；自由模板只用于用户确认的开放资源或仓库已经明确裁定的来源类型。

不要因为字段相似而猜模板，不要把无法理解的结构全部塞进`简介`，也不要把普通自由字段误写成自由特性。区分：

- 简介/风味：描述性文字；
- 普通字段：位阶、属性、闪避、武器、优势等可检索标量；
- 特性：带名称/原文/规则描述的有序规则块；
- 包级资料：许可、署名、包说明和目标系统，不是卡面字段。

对于自由模板，严格按当前 Schema 判断固定字段、任意标量字段和`内容`结构，不能沿用旧版本印象。

## 字段映射

从目标模板的 `defaultData` 开始构造数据，并与当前 Schema 对照：

- 保留所有要求字段，即使来源确实缺失而值为空；
- 不创造来源没有的译名、规则、原文或数值；
- 数组和对象保持结构，禁止把它们 JSON stringify 成表格里的长字符串；
- 数字若 Schema 要求字符串，就保存为字符串；
- 原字段含义不确定时保留原文片段并请求裁定；
- 不用拼写近似的别名、旧字段名或展示标签代替 Schema 键名。

## 拆分、合并与身份

一条来源记录不一定等于一条 PBRES 资源。只有仓库已有裁定或用户确认时才拆分/合并，例如多等级子职业、同一种族的多张特性卡。相同名称不自动代表重复项。

尽量保留稳定来源 ID、原顺序和目录语义。需要新 ID 时使用仓库既有生成方式。对每个来源块记录唯一终态：

- `converted`：已明确转换；
- `skipped`：经确认不是资源或明确重复；
- `pending`：需用户裁定。

三类数量之和必须等于盘点出的候选来源块数。

## 一次性提取脚本

仅当同类资源数量较大且中间文本已经统一时使用。脚本应：

- 只读取统一后的副本，不读取或改写原件；
- 对未知标题、缺字段、重复 ID、异常块和未消费文本立即报错；
- 输出确定顺序和可比较 JSON；
- 生成数量与异常报告；
- 先在少量样本上验证，再跑全量；
- 存放在任务 `.scratch`，任务后不成为技能或长期权威生成器。

提取成功只证明语法匹配，不证明语义正确，仍需人工对照和卡面验收。

## 必须询问用户

以下情况必须暂停相关记录，并提供来源上下文、候选方案及各自影响：

- 未知/非标准资源类型，或不知道使用哪个模板；
- 一个块可能是多个资源，或多个块可能应合并；
- 普通字段、简介、特性之间的归属不明确；
- 需要翻译、缩写、补写、删减或改规则才能容纳；
- 图片与资源无法唯一对应，或需要主观裁剪；
- 包边界、目录层级、稳定 ID、替换关系不明确；
- 署名或许可信息缺失且会影响交付；
- Adapter 报告未裁定损失。

询问时不要只列一个孤立词条；展示足够的前后文、拟映射字段以及建议选项，让用户能判断。
